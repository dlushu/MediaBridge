# ADR-0066 破坏性数据变更只有一条路：注册迁移任务，禁止在模块内偷接

- 状态：已采纳
- 相关：[0047](0047-data-migration-gate.md)（迁移框架本体）、[0046](0046-plugin-multiple-types.md)（v1→v2 那个任务的来源）

## 背景

数据版本从 v1 升到 v2 时，[0047](0047-data-migration-gate.md) 立了通用迁移框架：版本门禁、预检、交互入口、提交点、断点续跑。v1→v2 就是这么跑的 —— 任务在
`server/core/migrations/tasks/0002-plugin-types.js`，数据版本 1 → 2。

框架之外还有一条「顺手就接」的路径：业务模块自己维护一个私有 schema 版本号，读到老形状就地修补。`emby.db` 走的就是这条 —— 库内 `meta.schema_version`（当前 5）配一句幂等的 `ALTER TABLE` 加列（[db.js](../../server/modules/emby/db.js) 的 3 → 4 加 `hidden`）。

两条路并存，遇到「破坏性数据变更」（改写已有数据的值 / 位置 / 键）时，很容易沿更省事的那条走 —— 在模块里加一句修补，而不是注册迁移任务。丢掉的不只是这一次的便利，而是框架的全部保障：没有门禁拦住半迁移的进程，没有预检与交互入口，失败后没有现场也没有断点，出问题连「数据停在哪一版」都说不清。

## 决定

**破坏性数据变更只有一条路：新增迁移任务 `server/core/migrations/tasks/NNNN-*.js`（B1），数据版本逐 1 递增。**

1. 只要改动**已有数据**（改写行的值、迁移文件 / 目录位置、改键名、改编码或前缀），一律注册迁移任务；同时把 [index.js](../../server/core/migrations/index.js) 的 `CURRENT_DATA_VERSION` 文件序号取下一个整数（框架对缺号 / 乱序拒启）。
2. **禁止**在业务模块内做上述改写的就地修补；**禁止**借模块私有的 schema 版本号搬迁数据；**禁止**在启动流程里散落迁移代码。
3. 边缘划清：模块私有的、**只增不改存量**的 DDL（加列 / 加表 / 加索引）留在模块内，用 `CREATE TABLE IF NOT EXISTS` + 幂等 `ALTER TABLE`（配 `hasColumn` 这类判据）即可 —— 它定义的是「库的形状」，不搬迁数据，也不需要门禁与向导。**分界线是「有没有改写既有数据」**：没有 → 模块内；有 → 框架。
4. 该口径长期适用，不再逐次讨论。
5. **交互口径沿用 [0047](0047-data-migration-gate.md) 第 4 节**：迁移任务注册后，预检**无冲突就静默迁移**（服务端启动时自动跑完再启业务，不必等有人打开面板），**只有预检出现要人决定的冲突**（如同 id 多包）才铺向导走交互，且向导只列要决定的那几项。迁移任务本身不各自定义交互方式。

## 理由

- 破坏性变更天然是「跑一半会坏」的操作，一致性只能靠门禁（业务在迁移完成前不启动）+ 提交点（整任务成功才升版本）+ 幂等步骤（可断点续跑）三件套兜住；模块内的就地修补这三样一样没有。
- 「数据当前是什么版本」需要唯一真源。多版本各迁各的，会出现模块私有版本与全局版本各说各话，还原备份或降级时无从判断整体一致性。

## 后果

- 每一次破坏性变更自动获得门禁三态、预检、交互入口、提交点与断点续跑，不必重造。
- 数据版本只有 `data/.data-version` 一个真源，模块不再需要承载「这份数据是哪个时代」的知识。
- 代价是新增破坏性变更时必须写幂等步骤，并接受「数据落后就被门禁拦住、业务暂不启动」；换来的是可恢复、可审计。
- 新装与老装走同一条判断（全新安装直接写当前版本、不跑迁移，见 0047），不为「有没有装过」分叉。

## 备选（已否决）

- **模块内自增 schema 版本搬迁数据**（借用 `emby.db` 的 `SCHEMA_VERSION` 那条路）：模块私有、没有门禁与向导；多个模块各自演进时，无人知道全局该停在哪一版。否决。
- **每模块各挂一个版本号、各迁各的**：与「一个面板一份数据、一个总版本」的事实不符，还原备份 / 降级时无从判断整体一致性。否决。
- **每次破坏性变更都临时写脚本，不进 `tasks/`**：一次性脚本没有提交点，跑一半失败就没有续跑依据。否决。
