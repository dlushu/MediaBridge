# ADR-0078 段级对象一律单连接直搬；切块档只留给真·大文件

- 状态：已采纳
- 相关：[0077](0077-relay-small-object-single-connection.md)（本文改的是它的"一块"这条线）、
  [0045](0045-relay-chunked-concurrent.md)（第 1 步再改一次）、
  [0050](0050-relay-chunk-policy-aligned-with-worker.md)（取块口径未动）、
  [0042](0042-auth-line-byte-relay.md) / [0044](0044-emby-stream-playvia-relay.md)（同一份中继的两处入口）

## 背景

0077 把"先探一发再重下"合并成一发，但直搬的线划在**一块**（`chunkKB`，默认 512KB）：比一块大的对象
仍然进切块档。上线后实测（Pornhub HLS、1080p，就是清单里 1.1~2.8MB 的那批分片）：

- 只有第一片 177KB 走了直搬（那片是下完的）；**其余每片都下到一半被播放器掐掉**：
  开始写「共 2930168 字节」，结束时只「搬了 0.5MB」；同一部片子清单被重取了 3 次（三个 `sid`），
  播放器在追进度、追不上就丢当前片。
- 切块档**必须按序吐**：第 1 块没读满，后面 15 路即使下完也一个字节都发不出去。某一块慢 / 走重试
  （到点判死是头部 10s、普通 30s）时，整条流在那一段就是**硬停顿** —— 播放器缓冲区只有几秒，
  等不到字节就掐连接。
- **单连接没有这种停顿**：慢也是**连续地慢**。同一批分片直连上游（带 Referer）首字节 302 / 291 / 311ms、
  511KB 那片 726ms 下完 —— 对段级对象来说，一条流是够的。

## 决定

1. **直搬的线从"一块"抬到 8MB**（`RELAY_DIRECT_MAX_BYTES`）：客户端这一发逻辑上要的数据不超过它，
   就**单连接流式**，不切块、不探、不重下。HLS 分片（段级对象）正落这一档。
2. **比上限还大的对象，那一发不掐**：它当**流式前缀**边下边发，剩下的字节由切块档从
   `prefix.end + 1` 起并发取、按序续上 —— 客户端从第 0 个字节起就有连续数据，上游那一发也不白拉。
3. **有前缀时不开"首块自适应 + 头部对冲"**：这两种是给"起播第一块"用的（治一过性拒连），
   前缀已经在连续吐字节了，再留着只是同一份数据多打几发。
4. 其余不变：第一发仍是"既是问路也可能是数据"（0077）；切块档的慢判死 / 超时 / 重试口径不变（0050）；
   上游不认 Range、探不出总长、`HEAD`、后缀式 `bytes=-N` 仍走单连接透传。

## 理由

- **按"对象是不是段级"分流，而不是按"块数"**：`chunkKB` 是**搬运粒度**（内存窗口 = `threads × chunkKB`），
  本来不该兼任"要不要切"的判据。段级对象（一片几 MB）要的是"别断流"，真·大文件（几 GB）要的是
  "并发把管道喂满"，两者判据不同。
- **停顿是切块档的固有代价，不是参数问题**：只要输出必须按序，任何一块的慢 / 重试都会变成整条流的空洞；
  把窗口调大、把重试调快都治不了"那一块就是没来"。
- **请求数顺带降下来**：一片 2.8MB 从"1 探测 + 12 发（含头部对冲的重复）"变成 **1 发**，
  上游侧的压力与风控风险都更低。

## 备选

- **只把重试 / 超时调小**：治不了"等一块"的空洞 —— 空洞还在、只是短一点，播放器掐连接的动作不会消失。**没选**。
- **让切块档容忍乱序（缓存乱序块、补齐再吐）**：顺序是响应体的语义，客户端要的就是从 `start` 起的连续字节，
  乱序没有意义。**没选**。
- **HLS 分片一律直搬、不看大小**：省掉判据，但 4K 高码率分片能到十几 MB，一条流跑满时并发才是必要的 ——
  上限之外那一档（前缀 + 并发）正是给它留的。**没选**（等价于把上限调到无穷）。
- **上限做成面板设置 / URL 参数**：多一个旋钮就多一处要解释的口径，而"8MB 以内一条流、以上并发"
  在实测这批清单上已经够用；真遇到更大的分片，把 `chunkKB` 调大即可让切块粒度跟着变粗。**暂不**（留作后续）。

## 后果

- **0077 的"一块"这条线被改**：直搬判据从 `chunkKB` 换成 `RELAY_DIRECT_MAX_BYTES`；
  0077 的"探测与取数据合并成一发"保留。
- **0045 第 1 步再改一次**：大对象那一发不再"掐掉重下"，而是当流式前缀用。
- **面板与外部字节代理（Worker）的骨架差异变大**：代理没有前缀流式这一步（仍是探针 → 切块）；
  取块的超时 / 失败口径（[0050](0050-relay-chunk-policy-aligned-with-worker.md)）仍然一致。
- **上限之外的对象会多占一条上游连接**（前缀那条），并在开头就并发取块；内存窗口仍是 `threads × chunkKB`。
- **日志**：直搬打 `⇄ 中继 … → 200（…，单连接直搬，共 N 字节）`；切块档打
  `…（前缀 8.0MB 流式 + 512KB × 16 路，共 N 字节）`；结束那行改成 `搬了 X / 共 Y`，
  **搬少了会写明"客户端提前断开"** —— 这次实测踩到的就是那种对不上的日志。
- **512KB~8MB 之间不再并发**：这些对象的耗时从"多路并发"变成"一条流"，带宽充裕时略慢，
  但不会再有按序停顿 —— 实测同一批分片单连接是够的。
