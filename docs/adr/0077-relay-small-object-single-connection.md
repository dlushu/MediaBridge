# ADR-0077 小对象单连接直搬：把"先探一发再重下"改成"一发决断"

- 状态：已采纳（"一块"这条直搬线与大对象"掐掉重下"由 [0078](0078-segment-object-single-connection.md) 改；
  "探测与取数据合并成一发"这一条保留）
- 相关：[0045](0045-relay-chunked-concurrent.md)（本文改的是它第 1 步：探测与"取第一块"合并）、
  [0078](0078-segment-object-single-connection.md)（改本文的直搬线与大对象那一支）、
  [0042](0042-auth-line-byte-relay.md) / [0044](0044-emby-stream-playvia-relay.md)（同一份中继的两处入口）、
  [0050](0050-relay-chunk-policy-aligned-with-worker.md)（取块口径未动）

## 背景

0045 定的骨架是"探总长 → 有界 Range 切块 → 多路在飞 → 按序吐"，对**网盘那种大文件**是对的：
上游按 Range 形态限速，开放式 `bytes=0-` 只有 ~0.1MB/s，必须让每一发都变成有界 Range。

但这套骨架是按**大文件**设计的，而 HLS 是**逐分片**取：每一片都要重走一遍"探一发 → 掐掉 → 按块切 → 按序拼"。
分片越小，这一步的浪费越突出 —— 同一份 1080p 清单、同一批分片实测：

| 口径 | 分片 1（180KB） | 分片 2（511KB） | 分片 3（191KB） |
|---|---|---|---|
| 直连上游（带 Referer），首字节 | 302ms | 291ms | 311ms |
| 经面板中继，首字节 | 1089ms | 1133ms | 875ms |
| 下完：直连 | 677ms | 726ms | 518ms |
| 下完：经面板 | — | 1.9s | — |

浪费在三处，都是**小分片**才放大的：

1. **探测那一发**（`bytes=0-1023`）为拿总长多一个 RTT，拿到就把连接掐掉 —— 紧接着又从头要一遍同样的字节。
2. **头部对冲**：前 4 块各发 2 路取先成功者（治大文件起播被一过性拒连卡住）。小分片本来就只有一块，等于同一片打两发。
3. **整块读满才吐**：客户端要等第一块（探测式请求取 256KB）**读满**才见第一个字节；比它小的分片等于整份读进内存才开写，而直连是边下边发。

播放器缓冲区只有几秒，每一片都多等近一秒，就是一顿一顿。

## 决定

`relayBytes` 的第一发改成**既是问路、也可能就是数据**：按"装得下一块（`chunkKB`）"的**有界** Range 去要，
回来再看响应头决定落哪档：

> ⚠️ **这条"一块"的线被 [0078](0078-segment-object-single-connection.md) 改成 8MB**
> （实测 HLS 分片有 1.1~2.8MB，卡在一块上就掉进切块档、按序等块、被播放器掐连接）；
> 第 2 步的"掐掉这一发"也改成"留着当流式前缀"。本文保留原样，只当历史。

1. **整份装得下**（`content-range` 的总长 ≤ 一块，且这一发确实覆盖了客户端要的那一段）→
   **单连接原样边下边发**，不再重下。客户端没给出可用的 Range 时收成 200 整份（206 是"部分内容"），
   给了就如实回 206 + `Content-Range`。
2. **装不下** → **掐掉这一发**（一个字节都不读），用它的 `content-range` 拿总长，开 0045 那套切块并发。
   上游请求数与改前相同（以前是"探一发 + 切块"，现在是"掐一发 + 切块"）。
3. **200 / 416**（上游不认 Range / 越界）→ 这一发就是如实的答案，原样搬走。
4. **形状认不出 / 取不回来** → 退回单连接原样透传（`relayPipe`），与改前一致。

`HEAD` 与 `bytes=-N` 后缀式 Range 直接走单连接透传：前者一个字节都不搬（还省掉一次问路），
后者**本身就有界**（不是被限速的开放式形态），上游自己算尾段比先探总长再切更省。

判据取 `chunkKB` 而**不另开设置项**：装得下一块 = 切块只会切出一块，切块并发在这一档没有任何收益。

## 理由

- **按对象大小分流，而不是按"这条线路是不是网盘"猜**：面板只看得见响应头，看不见上游是谁；
  总长与"认不认 Range"是唯一拿得到的判据，也正好是决定"要不要切"的那两个量。
- **仍然是"每一发都有界 Range"**：小对象那一发也是有界形态，0045 要治的限速没有被改回去 ——
  反而比"客户端带 Referer 直连"更稳（播放器自己发的常常是开放式 `bytes=0-`）。
- **首字节 = 一次上游往返**：小分片不再有"探测 + 重下"，也不再等整块读满。

## 备选

- **只在客户端带了有界 Range 时直搬**：改动最小，但 HLS 播放器多数**不带 Range**（整片 GET），
  报告里的三片正好全落在"帮不上"那一档。**没选**。
- **HLS 分片一律当小对象单连接搬**：省掉判据，但 HLS 里同样有 4K 高码率的大分片（一片几 MB），
  一律单连接等于把它推回网盘 CDN 限速那一档。**没选**。
- **直搬上限放宽到"几块"**：默认 512KB~1MB 这一段现在会落到切块档，请求数反而比单连接多
  （前 4 块各 2 路对冲）。放宽能一并吃掉这一段，但"放宽到多少"没有实测依据，先按"一块"这条
  可判定的线走；`chunkKB` 本身就是那个旋钮。**留作后续**。
- **保留探测、只在探测之后判小**：探测那一发的 RTT 与"掐掉再重下"正是本文要消掉的东西。**没选**。

## 后果

- **0045 第 1 步被改**：探测不再是独立的一发，与"取第一块"合并；0045 的第 2~4 步（切块 / 兜底 / 断开）不变。
- **面板与外部字节代理（Worker）在这一步不再同构**：代理仍是"探针 → 切块"。取块的超时与失败口径
  （[0050](0050-relay-chunk-policy-aligned-with-worker.md)）没有动，两边仍然一致。
- **日志能看出落哪一档**：小对象打 `⇄ 中继 … → 200（…，小对象单连接直搬，共 N 字节）`；
  切块档照旧打 `… （512KB × 16 路，共 N 字节）`。
- **一块到四块之间（默认 512KB~1MB）仍是切块档**：请求数与改前相同、不比改前差，但比单连接直搬多几发；
  分片普遍落在这一段时，把 `chunkKB` 调大即可把直搬上限一起抬高（判据跟着它走，不另设开关）。
- **上游可能白推几十~几百 KB**：大对象那一发被掐掉时，上游多半已经往连接里塞了一些字节。
  它只发生在"装不下"的大对象上（小分片没有这一发），相对整份大小可以忽略。
