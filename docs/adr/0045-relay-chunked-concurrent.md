# ADR-0045 字节中继改分块并发：把开放式 Range 换成有界 Range

- 状态：已采纳（第 1 步"先探一发再重下"被 [0077](0077-relay-small-object-single-connection.md) 改为一发决断，
  该步的直搬线与大对象那一支再由 [0078](0078-segment-object-single-connection.md) 改）
- 相关：[0042](0042-auth-line-byte-relay.md)（本文改的是它第 3 条约束的实现）、[0044](0044-emby-stream-playvia-relay.md)（同一份中继的另一处入口）、[0077](0077-relay-small-object-single-connection.md) / [0078](0078-segment-object-single-connection.md)（改本文第 1 步）

## 背景

0042 定的口径是"只搬运，不做流量管理"：把客户端的 Range 原样透传、单连接 `pipe`。上线后实测**播放慢**，根因不在面板的转发开销，而在**上游对 Range 形态的限速**（源插件 driver 里也实测记着）：

| 请求形态 | 实测速率 |
|---|---|
| 开放式 `Range: bytes=0-`（播放器默认，或干脆不带 Range） | ~0.1MB/s |
| 有界 `Range: bytes=N-M` | ~3.5MB/s |

猫爪引擎自己的代理早就吃透了这一点：探一发拿总长 → 按块切（网盘档 512KB）→ 多路并发发有界 Range → 按序吐，块落本地磁盘缓存。

## 决定

`relayBytes` 默认走**分块并发**，单连接透传降级为兜底：

1. ~~探一发 `Range: bytes=0-1023`，只为拿总长与"认不认 Range"（**先看状态再断流**，读完即断）。~~
   **改为**（[0077](0077-relay-small-object-single-connection.md)；直搬线与大对象那一支再由
   [0078](0078-segment-object-single-connection.md) 改）：第一发就按**直搬上限**（现为 8MB）的有界 Range 去要 ——
   整份装得下（HLS 分片这一档）就单连接边下边发；装不下就**把它当流式前缀**边吐边并发取后面的块，
   并用它的 `content-range` 拿总长接着走第 2 步。
2. 认 → 按 `chunkKB` 切块，**保持 `threads` 路在飞**，完成块**按序**写回客户端；内存只留 `threads × chunkKB` 的滚动窗口，背压交给 `pipeline`。
3. 不认 / 探不出总长 / 设置里关掉开关 → **退回单连接原样透传**（与 0042 完全一致，至少不变差）。
4. 客户端断开 → 整个窗口的上游连接一起断。

参数默认 **16 路 / 512KB**（与引擎网盘档对齐）。取值的优先级：**拉流地址上的查询参数（`?threads=&chunkKB=`）> 源插件 `play` 返回里带的 > 面板设置 `streamRelay` > 默认**。三个外部入口各管一件事：URL 参数管"这一次播放"，面板设置管"这台机器的默认"，`play` 返回管"这条线路需要"。

`proxy` 的清单档（子地址那一档）**参数跟着 `sid` 存**：分片是客户端照着清单取的，URL 上多挂两个参数既不保证带得回来，也把"这一份清单用什么参数搬"散到几十条地址上；所以清单那一跳定下来，分片那几十发共用。

## 理由

- 慢的是**形态**，不是"面板转发"这件事：让每一发都变成有界 Range，速率就上来了。
- 放在 `relayBytes` 一处：agg 流端点与 Emby 流端点共用同一份实现，改一次两边都受益；`play` 里多两个可选字段是向后兼容的，插件契约不用改。
- 不做磁盘缓存、不做跨分片预取：先解决"每一发被限速"这一个问题，别的等实测数据再说。

## 备选

- **委托猫爪引擎 / 插件去代理**：引擎那套（探测 + 并发 + 磁盘缓存 + 逐块重试）已被验证，但要走插件 ingress、多一跳，还要把带 Cookie 的载荷编进它私有的 `pst` 参数 —— 等于把"能不能播"耦合到实例进程是否在跑。**没选**。
- **只把开放式 Range 改写成逐块有界拉（不并发）**：改动最小、也能拿到 ~3.5MB/s 那一档，但 4K 高码率没有余量。**没选**：把 `threads` 填 1 就是它，留作降级档。

## 后果

- **0042 第 3 条约束被改**：不再"不做分块并发"，而是"默认分块并发，探不出总长才退回单连接"。
- 每条流多一次探测请求（1KB）；HLS 逐分片请求也会各探一次 —— 换来的是每一发都不再撞限速。
  （**0077 起**：探测不再单独发，与"取第一块"合并；**0078 起**：8MB 以内的对象整份直搬、不重下，
  更大的把那一发当流式前缀用 —— 切块档只管上限之外的尾部。）
- 并发是**对上游**的（默认 16 路/流）：网盘风控是这条路的现实风险，所以留了面板设置与 `play` 覆盖两个旋钮，默认值取引擎验证过的 16/512。
- 日志能看出档位：`⇄ 中继 … → 206（512KB × 16 路，共 N 字节）` / `⇄ 中继结束 …：搬了 x MB（512KB × 16 路）`。
